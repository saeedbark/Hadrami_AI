Abdelwedoud Bark

Abstract

Hadrami Arabic, spoken by an estimated five to seven million people in Hadhramaut and the Hadrami diaspora, has almost no published NLP resources. We release the first verified Hadrami lexicon (1,000 entries, all with MSA glosses and explanatory definitions, 99.6% with Hadrami–MSA example pairs, 8.6% with attested proverbs, all with 768-dim Gemini embeddings) and Hadrami-RAG, a retrieval-grounded conversational system that auto-classifies five user intents (single-word lookup, paragraph translation, definition, semantic search, open Q&A) and refuses to answer outside the lexicon's evidence. We accompany the system with a Flutter mobile application that doubles as a human-in-the-loop curation pipeline. The paper describes the resource, the system architecture, the empirical evaluation protocol, and a public venue for displaying ongoing native-speaker evaluation.

1  Introduction

Modern Arabic NLP overwhelmingly targets Modern Standard Arabic (MSA) and a handful of high-resource regional dialects (Egyptian, Levantine, Gulf). Within the Yemeni dialect group, Hadrami — the variety of the Hadhramaut governorate and a centuries-old diaspora across the Indian Ocean rim — has, to our knowledge, no publicly available lexicon, parallel corpus, or dialect-aware NLP system. The few existing resources (Watson 2002; Al-Saqqaf 2006) are linguistic descriptions, not machine-consumable datasets.

Two practical consequences follow. First, large multilingual models fluently hallucinate Hadrami semantics: when prompted with a fabricated Hadrami-shaped string, frontier LLMs typically respond with a plausible-sounding but wholly invented gloss. Second, native speakers who would benefit from a usable Hadrami–MSA tool have nowhere to turn: the closest publicly hosted services treat Hadrami input as either MSA (mistranslating) or as Egyptian / Gulf (inserting unrelated lexicon).

This paper contributes, in publishability order:

  1. A verified Hadrami lexicon (resource). 1,000 curated headwords with MSA equivalents, definitions, examples, regional tags, and 768-dim semantic embeddings. Released under CC BY 4.0 alongside the human evaluation pairs (§5).
  2. A retrieval-grounded conversational system. A unified chat dispatcher that routes each user message into one of five intents and answers strictly from retrieval evidence, with a confidence-gated unknown-word short-circuit that produces a suggest-this-word response rather than inventing a meaning.
  3. A deployed Flutter application. A mobile front-end that lets native speakers query and contribute to the lexicon, used here as the recruitment and data-collection surface for the human evaluation in §6.6 and the in-app evaluation dashboard in Appendix A.

The hallucination experiment in §6.4 is the headline empirical claim: on a controlled set of 50 fabricated Hadrami-shaped strings, baseline LLMs invent meanings; the Hadrami-RAG pipeline refuses or emits a suggest-word block.

2  Related Work

2.1  Arabic dialect resources

The MADAR corpus (Bouamor et al., 2018) covers 25 Arab cities including Sana’a but not Hadhramaut. ADIDA (Salameh et al., 2018) and the QADI corpus (Abdelali et al., 2021) treat dialect identification at country granularity, with Yemeni examples drawn predominantly from Sana’ani sources. NADI shared tasks (Abdul-Mageed et al., 2020, 2021, 2022) similarly aggregate Yemen as a single label. Of the resources we surveyed, none contains a curated Hadrami lexicon with MSA alignment.

2.2  Lexicon-grounded translation

Bilingual dictionary induction (Rapp, 1995; Artetxe et al., 2018) and retrieval-augmented dialectal MT (Khalifa et al., 2021) both rely on the assumption that a dictionary-aligned lexicon exists. For low-resource dialects this assumption is itself the open problem; our resource fills that gap for Hadrami and the system shows the lexicon is sufficient to ground a conversational model on sentence-level paragraphs.

2.3  Retrieval-augmented generation and grounded refusal

RAG (Lewis et al., 2020), Self-RAG (Asai et al., 2023), and the ``when do retrievers help'' analysis (Mallen et al., 2023) all motivate the use of explicit retrieval evidence. Our contribution on top of this line is the refusal contract: a confidence gate that, on retrieval scores below a threshold, short-circuits to a suggest-this- word block instead of allowing the LLM to free-generate.

2.4  Yemeni Arabic linguistic descriptions

Watson (2002) provides the canonical phonology of San’ani; Al-Saqqaf (2006) is the most cited descriptive work on Hadrami specifically. Both are linguistic, not computational, references; we cite them for attestation of the dialect features that motivate our coverage choices (e.g., the أم حبيل /spider/ entry, §7).

3.2  Curation protocol

Each entry passes through three stages. (i) Headword proposal from a literature pass plus elicitation with the diaspora community. (ii) Field completion: MSA equivalent, Arabic definition, ≥1 example pair, regional tag, POS. (iii) Embedding via the gemini-embedding-001 model on a canonical document (versioned EMBEDDING_DOC_VERSION = "v2") that concatenates headword, MSA equivalent, definition, and the first example. Entries failing any stage have embedding_dirty = true until the next sync run regenerates the vector.

3.3  Feedback loop

The Flutter app exposes a feedback endpoint that captures two kinds of user submissions: corrections to existing entries and proposals for new headwords. As of compilation date, the feedback table contains 10 rows: 5 correction and 5 new_word, all with status = open awaiting reviewer triage. This loop is the resource's growth path; we report on it as the ``mobile-deployment as a curation pipeline'' angle in §4.4.

4  System Architecture

4.1  Overview

Hadrami-RAG is a single FastAPI service backed by Supabase (Postgres + pgvector), with a Flutter client. A unified /chat endpoint replaces the earlier /ask and /translate-phrase endpoints. Figure 1 sketches the request flow.

4.2  Intent classifier

Five intents cover the chat surface, each with a deterministic regex / heuristic classifier. Table 4 summarises the cues.

Table 4. Intent rules implemented in system_prompt.py:intent_for.
IntentTriggerRouted to
wordsingle Hadrami token, no MSA marker, no question particleretrieve_rag_context → word prompt
translateexplicit ترجم / ``translate'', or paragraph ≥ 8 chars with sentence punctuationretrieve_phrase_context → translation prompt
defineما معنى / اشرح / ``what does X mean''retrieve_rag_context → definition prompt
semanticكلمة تعني / أداة ل (gloss-first descriptions)vector-only retrieval → semantic prompt
qaopen question; default fall-throughretrieve_rag_context → QA prompt

4.3  Retrieval

Retrieval is hybrid. The keyword path uses a Supabase RPC over the word_clean / word_vocalized columns with diacritic-stripping normalisation and prefix matching. The vector path embeds the user query with gemini-embedding-001 and performs a pgvector cosine search against the entries table. Results are merged with a stable rank-fusion that prefers exact keyword hits while preserving vector hits for semantic intent. For paragraph translation (input ≥ 80 chars) the dispatcher additionally splits on Arabic and Latin sentence punctuation and re-runs retrieval per sentence, then deduplicates — this is the change that lets the pipeline recover lexical anchors that would be lost in a whole-paragraph embedding.

4.4  Confidence gate and suggest-word block

When the merged top retrieval score falls below RAG_CONFIDENCE_GATE (default 0.65) and the intent is word, define, or translate with a single OOV headword, the dispatcher short-circuits to a deterministic suggest-this-word reply. No LLM call is made. This is the mechanism that gives Hadrami-RAG its hallucination-resistance property.

4.5  LLM fallback chain

Generation defaults to gemini-2.5-flash with deterministic fallback to gemini-2.0-flash and gemini-2.5-flash-lite on rate-limit or transient failure. gemini-1.5-flash was removed from the chain on 2026-05-03 after it began returning NotFound on the v1beta endpoint. When all chain members fail, the pipeline emits a deterministic ``model unavailable, lexicon-fallback'' message rather than masking the failure.

4.6  Mobile deployment as a curation pipeline

The Flutter client renders the dispatcher's intent, suggest_word, and answer_source fields as per-message badges, so users can distinguish a lexicon-grounded reply from a model-generated one. The same client surface drives /feedback submissions (Table 1, §3.3) and the in-app evaluation dashboard described in Appendix A.

6.4  Hallucination resistance (E4) — the headline experiment

HALL-test consists of 50 fabricated Hadrami-shaped strings, each chosen to look phonotactically plausible while not appearing in any attested Hadrami source. A correct response is defined as one of: (a) emit the suggest_word block, (b) decline to translate, (c) refuse with an explicit ``not in lexicon'' marker. Inventing a meaning counts as a hallucination.

7  Error Analysis

7.1  A worked paragraph example

We expand the running example used during system development.

Input (Hadrami):
اليوم شفت أم حبيل في السقف، قلت لاخوي إكس عليه وخله، لكنه أكشف وخاف منها.
Reference (MSA):
اليوم رأيت عنكبوتاً في السقف، فقلت لأخي تجاهله واتركه، لكنه كان عنيداً وخاف منه.

The dispatcher classifies this as translate and the paragraph-aware retriever returns the licensing pairs needed to ground each content word: 

vector_context q='أم حبيل...'  -> 6 hits:
  أُمّ حُبَيْل        -> العنكبوت            (0.71)
  إِكِّس عَلَيْه     -> تجاهله تماماً     (0.75)
  خَلَّوه          -> تركوه                  (0.71)
  فَزَع            -> خاف / خوف             (0.67)

All four content-word pairs are recovered, satisfying the grounding contract for sentence-level translation. However, on the compilation date the actual generation step failed: gemini-2.5-flash, gemini-2.0-flash, and gemini-2.5-flash-lite all returned ResourceExhausted within seconds of each other on the free-tier quota. The dispatcher correctly emitted the ``model unavailable, lexicon-fallback'' deterministic message rather than fabricating a translation. This is the intended failure mode but means we cannot report the actual translated string in this draft.

7.2  Categories of expected failure

  • Long paragraphs. The 80-char paragraph trigger helps, but inputs exceeding ~250 characters push the few-shot pair budget (16 pairs) and individual pairs may be truncated. Mitigation: bump retrieve_phrase_context's output cap and re-evaluate on a longer-input subset of TR-test.
  • Idiomatic phrases not in examples. The lexicon's coverage of multi-word expressions is captured by 46 Expression-POS entries (Table 2). Idioms outside this set are likely to be mis-translated word-by-word.
  • Code-switching with Latin script. The intent classifier handles English instruction prefixes; the retriever does not embed Latin tokens. Mitigation: strip Latin segments before retrieval, route the rest through the dispatcher.
  • Orthographic variants. word_clean normalisation handles diacritics and ligatures; it does not handle free-variant spellings (e.g., hamza placement). Mitigation: the phonetic_variants jsonb field is reserved but underpopulated.
  • Region-specific terms. The 96.7% general-region default (Table 3) under-represents coastal vs. wadi vs. interior contrasts, so the retriever cannot filter by region today. The ``other'' singletons in Table 3 hint at the eventual partition.

8  Limitations and Ethics

8.1  Coverage

1,000 entries is small even for a low-resource dialect; rare words, recent neologisms, and proper-noun toponyms are deliberately out of scope. The lexicon is biased toward domestic and rural vocabulary reflecting the curator's own networks; reviewer recruitment for the Flutter app prioritises diasporic and coastal speakers to reduce this skew.

8.2  Reviewer demographics

At submission time the resource will list reviewer count, age band, gender distribution, and self-reported region (coastal / wadi / interior / diaspora). No personally identifying information is published.

8.3  Consent and data subject rights

The Flutter app's /feedback endpoint records corrections and new-word suggestions with consent at submission time. IPs are truncated server-side; raw IPs do not enter the database. Reviewers in the human-evaluation loop sign a participation agreement that permits aggregated publication of their ratings without identifying details.

8.4  Closed-model dependency

Generation depends on the Gemini API. On free-tier credentials the pipeline degrades to a deterministic lexicon-fallback message rather than a silent failure (§6.4 documents an instance encountered during the writing of this draft). For long-term reproducibility we intend to evaluate an open-weights drop-in (Jais, Aya 23) in future work.

8.5  Risk of misuse

A dialectal MT system carries the usual risks of mistranslation in consequential settings (legal, medical). The deployed app surfaces an explicit warning that Hadrami-RAG is for educational and community-curation use, not for high-stakes translation.

9  Conclusion and Future Work

We released the first machine-consumable Hadrami lexicon (1,000 entries, full MSA glosses, 99.6% example coverage, 768-dim embeddings) and a retrieval-grounded conversational system whose hallmark is a refusal contract: when retrieval evidence is insufficient, the dispatcher emits a deterministic suggest-this-word block instead of a fabricated meaning. Engineering health is documented (42/42 tests passing); empirical numbers are partitioned into measured, smoke-test, and TBD cells with explicit script-level provenance.

Three priorities follow. (i) Recruit two native-speaker reviewers, promote the candidate test sets at backend/tests/fixtures/{wl,tr,int}_test.candidate.json to canonical fixtures, and run E1–E5 to fill Tables 8–12. (ii) Re-embed the corpus with the v2 document layout (EMBEDDING_DOC_VERSION = "v2") and run E6 to compare Gemini, LaBSE, and multilingual-e5 retrievers. (iii) Ship the in-app evaluation dashboard described in Appendix A and begin populating Table 13 from real reviewer ratings.

Appendix A — Where reviewer evaluation results live in the deployed app

When the application is published and language specialists begin testing, their ratings need three places to live, in increasing order of public visibility. The recommendation below mirrors the answer given to the design question that prompted this draft.

A.1  In-conversation grounding indicator

Every chat bubble already carries the dispatcher's intent, answer_source, and suggest_word fields. We surface a one-line badge under each reply: ``grounded in N lexicon entries'' for retrieval-backed replies and ``not in lexicon — suggest a new entry'' for refusals. The mechanism that makes the refusal contract visible is what makes it credible. This costs nothing per message and informs every user without requiring navigation.

A read-only screen reachable from Settings, fed by a JSON endpoint (/eval/summary) so it updates with each new evaluation run without an app release. Layout:

  evaluation_run_id text not null,        -- groups items into a session
  item_id         text not null,           -- TR-test / WL-test / HALL-test item id
  dimension       text not null            -- one of: accuracy, authenticity, helpfulness, refusal_correctness
                  check (dimension in ('accuracy','authenticity','helpfulness','refusal_correctness')),
  rating          int not null check (rating between 1 and 5),
  free_text       text,
  app_version     text,
  created_at      timestamptz not null default now()
);

create index evaluations_run_idx on evaluations (evaluation_run_id, dimension);
create unique index evaluations_unique on evaluations (reviewer_id, evaluation_run_id, item_id, dimension);

Aggregation lives in a server-side view that powers /eval/summary; raw rows are never sent to the client.

A.5  What not to do

  • Do not surface raw per-reviewer scores in-app. Reviewers may infer each other's identities at small N; aggregate before display.
  • Do not gate the chat behind ``ratings required''. The grounding badge in §A.1 is the only ratings-related UI on the chat surface; explicit ratings live in a separate ``Help us evaluate'' tab.
  • Do not mix ratings into the feedback table. Free-text corrections and structured ratings have different validation, retention, and aggregation needs; keeping them in separate tables is cheap insurance.
