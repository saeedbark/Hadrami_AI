الأسئلة التي تُفتَح بها كل مقابلة Flutter تقريبًا — وأشهر مواضع السقوط فيها.

BEGINNERما الفرق بين var و final و const؟
🎯 ماذا يختبر المُحاور؟هل تفهم الفرق بين وقت التصريف (compile-time) ووقت التشغيل (runtime)؟ هذا السؤال البسيط هو بوّابة لسؤال أعمق عن أداء Flutter.

var يستنتج النوع ويسمح بإعادة الإسناد. final يُسنَد مرّة واحدة وقت التشغيل. const قيمة معروفة بالكامل وقت التصريف، وتُبنى مرّة واحدة وتُشارَك (canonicalized). 

var a = 5;          a = 10;              // ✅ مسموح
final b = DateTime.now();                // ✅ قيمة runtime
b = DateTime.now();                      // ❌ خطأ تصريف

const c = DateTime.now();                // ❌ غير معروفة وقت التصريف
const d = [1, 2, 3];                     // ✅ ثابتة تمامًا

final list = [1, 2];  list.add(3);       // ✅ المرجع ثابت لا المحتوى
const list2 = [1, 2]; list2.add(3);      // ❌ استثناء وقت التشغيل

🎯 Senior follow-up: لماذا const مهمّ في Flutter تحديدًا؟

لأن الـWidget الـconst لا يُعاد بناؤه. Flutter يقارن بالمرجع (identical())، وبما أن Dart يُوحّد الكائنات الثابتة في نسخة واحدة (canonicalization) فإن المرجع نفسه يعود في كل build — فتتخطّى آلية المطابقة الغصن كاملًا. هذا يجعل const أداة أداء لا مجرّد أسلوب كتابة. تفصيله في قسم Rebuilds.

⚠️ Interview Trap

«final يعني القيمة لا تتغيّر» — خطأ. الذي لا يتغيّر هو المرجع. final List يمكن الإضافة إليه. لو أردت محتوًى غير قابل للتعديل فأنت تحتاج const أو List.unmodifiable أو حزمة immutability.

BEGINNERما هي Null Safety؟ وما دور late و ? و !؟
🎯 ماذا يختبر المُحاور؟هل تعرف أن null safety في Dart هي sound — أي أن المُصرِّف يضمنها فعلًا ولا يكتفي بالتحذير؟ وهل تسيء استخدام !؟

Sound Null Safety تعني أن النوع String لا يمكن أن يحمل null إطلاقًا — والمُصرِّف يستطيع الاعتماد على ذلك في التحسين، لا مجرّد تنبيهك. 

String  a = null;   // ❌ خطأ تصريف
String? b = null;   // ✅ nullable

// ! = "أنا متأكّد أنها ليست null" — تأكيد أنت مسؤول عنه
final len = b!.length;        // يرمي إن كانت null

// late = "ستُسنَد قبل أول قراءة" — يؤجّل التهيئة لا يلغيها
late final Database db;       // تُسنَد في initState مثلًا

// ?. و ?? للتعامل الآمن
final n = b?.length ?? 0;

⚠️ Interview Trap: ! ليست حلًّا — هي نقل للمسؤولية

استخدام ! لإسكات المُصرِّف يحوّل خطأ تصريف (رخيص) إلى تعطّل وقت تشغيل عند المستخدم (باهظ). الإجابة القوية: «أستخدم ! فقط حين يكون لديّ ضمان لا يراه المُصرِّف — مثل قيمة أسندتُها في initState — وفي غير ذلك أعالج الـnull صراحةً.»

🎯 Senior follow-up: late بلا final؟

late وحدها تسمح بإعادة الإسناد وتؤجّل التهيئة — مفيدة للحقول المكلفة (lazy initialization): late final x = expensive(); لا تُنفَّذ إلا عند أول قراءة. لكن انتبه: قراءة late قبل الإسناد ترمي LateInitializationError وقت التشغيل، فأنت تستبدل أمان المُصرِّف بمرونة.

MID-LEVELما الفرق بين abstract class و mixin و interface في Dart؟
🎯 ماذا يختبر المُحاور؟هل تفهم أن Dart لا يملك كلمة interface أصلًا — أي صنف يصلح كواجهة؟ ومتى تختار كلًّا منها؟
abstract class Repository {        // عقد + تنفيذ مشترك محتمل
  Future<User> fetch(int id);
}

mixin Logger {                    // سلوك يُعاد استخدامه أفقيًّا
  void log(String m) => print('[$runtimeType] $m');
}

class ApiRepo extends Repository with Logger { ... }

// أي صنف يصلح كواجهة عبر implements
class FakeRepo implements Repository { ... }   // يجب تنفيذ كل شيء
الأداةاستخدمها حينالقيد
extendsعلاقة "is-a" حقيقية + وراثة تنفيذواحد فقط
implementsتريد العقد فقط بلا تنفيذيجب تنفيذ كل الأعضاء
with (mixin)سلوك مشترك عبر تسلسلات هرمية مختلفةترتيب الـmixins مهمّ (linearization)

🎯 Senior follow-up: ما مشكلة الإفراط في mixins؟

تُنشئ اقترانًا خفيًّا: الصنف يرث حقولًا ودوالّ لا تظهر في تعريفه، وترتيب with A, B يغيّر السلوك عند التعارض. القاعدة: mixin للسلوك عديم الحالة أو قليلها؛ وللحالة المشتركة استخدم التركيب (composition) لا الخلط. وفي Dart 3 صارت لديك sealed وfinal و base للتحكّم في من يرث ماذا — استخدمها لتوثيق نيّتك.

MID-LEVELما الجديد في Dart 3: Records و Pattern Matching و Sealed Classes؟
🎯 ماذا يختبر المُحاور؟هل تتابع تطوّر اللغة؟ سؤال شائع لتمييز من يكتب Dart حديثة عمّن توقّف عند 2.x.
// Records — قيم مركّبة بلا تعريف صنف
(int, String) pair = (1, 'a');
({int x, int y}) point = (x: 1, y: 2);
(String name, int age) getUser() => ('Sara', 30);
final (name, age) = getUser();          // destructuring

// Sealed classes — تسلسل مغلق يعرفه المُصرِّف
sealed class Result<T> {}
class Ok<T> extends Result<T> { final T value; Ok(this.value); }
class Err<T> extends Result<T> { final Object e; Err(this.e); }

// Pattern matching — exhaustive: المُصرِّف يمنعك من نسيان حالة
String render(Result<int> r) => switch (r) {
  Ok(value: final v) => 'نجح: $v',
  Err(e: final e)    => 'فشل: $e',
};   // لا حاجة إلى default — والمُصرِّف يخطئك إن أضفت نوعًا ونسيته

🎯 Senior follow-up: لماذا sealed أقوى من abstract هنا؟

لأن الاكتمال (exhaustiveness) يصير مضمونًا وقت التصريف. مع abstract تحتاج default، فحين تضيف حالة ثالثة (Loading) يمرّ الكود بصمت ويسقط في الـdefault. مع sealed يرفض المُصرِّف البناء حتى تعالج الحالة الجديدة في كل switch. هذا يحوّل فئة كاملة من الأخطاء من وقت التشغيل إلى وقت التصريف — وهي بالضبط الحجّة التي يريد المُحاور سماعها.

MID-LEVELما الفرق بين Exception و Error؟ ومتى تلتقط كلًّا منهما؟
🎯 ماذا يختبر المُحاور؟هل تلتقط catch (e) عشوائيًّا؟ هذا سؤال يكشف نضج التعامل مع الأخطاء بسرعة.

Exception = حالة متوقّعة يجب التعامل معها: انقطاع شبكة، ملف غير موجود، إدخال غير صالح. Error = خطأ برمجي لا يجب التقاطه بل إصلاحه: StateError، RangeError، AssertionError. 

try {
  await api.fetch();
} on SocketException {        // ✅ محدّد: أعرف ما أفعل
  showOffline();
} on FormatException {        // ✅ محدّد
  showParseError();
} catch (e, st) {             // ✅ الأخير: سجّل ثم أعد الرمي
  logger.error(e, st);
  rethrow;
}

⚠️ Interview Trap: catch (e) {} الفارغة

ابتلاع كل شيء بصمت هو أسوأ نمط في التعامل مع الأخطاء: يحوّل عطلًا واضحًا إلى سلوك غامض ويجعل التشخيص مستحيلًا. القاعدة: التقط ما تعرف كيف تعالجه؛ وما عداه سجّله وأعد رميه.

SENIORاشرح الـEvent Loop في Dart. ما الفرق بين Microtask Queue و Event Queue؟
🎯 ماذا يختبر المُحاور؟هذا هو السؤال الفاصل. المرشّح Mid يقول «async/await يجعل الكود غير متزامن». المرشّح Senior يشرح لماذا لا يجمّد await الواجهة، ولماذا قد تُجوّع microtask لا نهائية الواجهة.

Dart أحادي الخيط (single-threaded) داخل الـisolate الواحد. لا يوجد تنفيذ متوازٍ هنا — بل تناوب (concurrency) تديره حلقة الأحداث: 

            ┌─────────────────────────────────┐
            │          Dart Isolate           │
            │   ذاكرة خاصّة · لا تُشارَك       │
            │                                 │
            │   ┌───────────────────────┐     │
            │   │     Event Loop        │     │
            │   └───────────┬───────────┘     │
            │               │                 │
            │      ①  Microtask Queue         │
            │         (أولوية عليا)           │
            │         scheduleMicrotask        │
            │         Future.value().then      │
            │               ↓                 │
            │      ②  Event Queue             │
            │         I/O · timers · gestures  │
            │         Future من عملية خارجية   │
            └─────────────────────────────────┘

القاعدة الحاسمة:
  الحلقة تُفرغ Microtask Queue **بالكامل** قبل أن تلتقط
  حدثًا واحدًا من Event Queue.

مثال يُسأل عنه كثيرًا — ما ترتيب الطباعة؟

void main() {
  print('1');
  Future(() => print('2'));                 // Event Queue
  Future.microtask(() => print('3'));       // Microtask Queue
  Future.value().then((_) => print('4'));   // Microtask Queue
  print('5');
}
// الناتج: 1 · 5 · 3 · 4 · 2
// المتزامن أولًا، ثم كل الـmicrotasks بالترتيب، ثم أحداث الـEvent Queue.

🎯 لماذا يهمّ هذا عمليًّا في Flutter؟

لأن رسم الإطار (frame) يُجدوَل في Event Queue. فسلسلة microtasks طويلة أو متجدّدة تمنع الحلقة من الوصول إلى حدث الرسم أصلًا — فتتجمّد الواجهة رغم أن كل شيء "غير متزامن". هذه هي الإجابة التي تفصل من فهم الآلية عمّن حفظ الكلمات.

⚠️ Interview Trap: «async يعني في خيط آخر»

خطأ تمامًا. async/await لا يُنشئ خيطًا ولا يوازي شيئًا — هو سكّر نحوي (syntactic sugar) فوق الـFutures وحلقة الأحداث. حلقة for ثقيلة داخل دالّة async ستجمّد الواجهة تمامًا كما لو كانت متزامنة. المتوازي الحقيقي = Isolate.

SENIORما الفرق بين Concurrency و Parallelism؟ ومتى تستخدم Isolate؟
🎯 ماذا يختبر المُحاور؟الخلط بينهما من أشهر أخطاء المقابلات. ثمّ: هل تعرف متى يستحقّ Isolate تكلفته؟
Concurrency  = التعامل مع أشياء كثيرة بالتناوب على معالج واحد
               → async/await · Event Loop
               → يحلّ: الانتظار (I/O · شبكة · قرص)

Parallelism  = تنفيذ أشياء كثيرة في اللحظة نفسها على أنوية متعدّدة
               → Isolates
               → يحلّ: الحساب الثقيل (CPU-bound)

القاعدة العملية: إن كان الكود ينتظر، استخدم async. إن كان يحسب، استخدم Isolate. استخدام async لمهمّة حسابية لا يفيد شيئًا لأن الخيط نفسه مشغول. 

// مهمّة ثقيلة: فكّ JSON ضخم · معالجة صورة · تشفير
final result = await compute(parseHugeJson, jsonString);

// compute() غلاف مبسّط فوق Isolate.spawn.
// للتحكّم الكامل ولعدّة رسائل: Isolate.spawn + SendPort/ReceivePort

🎯 Senior follow-up: ما تكلفة Isolate؟ ولماذا لا تستخدمه دائمًا؟

كل isolate يملك ذاكرة خاصّة (heap) وحلقة أحداث خاصّة — لا يشارك الحالة إطلاقًا. النتائج:

  • إنشاؤه مكلف (ذاكرة + بدء).
  • الرسائل بينه وبين الرئيسي تُنسخ لا تُشارَك — نقل كائن ضخم قد يكلّف أكثر من الحساب نفسه.
  • لا يصلح لمهمّة أقصر من ~١٦ms؛ ستدفع النسخ أكثر ممّا توفّر.

الحدّ العملي: استخدمه حين تُظهر DevTools أن الحساب يتجاوز ميزانية الإطار ويسبّب jank. لا تخمّن — قِس.

MID-LEVELما الفرق بين Future و Stream؟ ومتى تختار كلًّا منهما؟
🎯 ماذا يختبر المُحاور؟هل تختار بناءً على عدد القيم عبر الزمن؟ وهل تعرف الفرق بين single-subscription و broadcast — لأنه سبب شائع لأخطاء غامضة.
Future  →  قيمة واحدة (أو خطأ) مستقبلًا       ──●
Stream  →  صفر أو أكثر عبر الزمن              ──●──●──●──|
// Future: نداء API واحد
Future<User> fetchUser(int id) async => ...;

// Stream: أحداث متتابعة
Stream<int> ticks() async* {
  for (var i = 0; ; i++) { await Future.delayed(Duration(seconds: 1)); yield i; }
}

// الأنواع:
final single = controller.stream;                    // مستمع واحد فقط
final multi  = StreamController<int>.broadcast();    // عدّة مستمعين

⚠️ Interview Trap: Bad state: Stream has already been listened to

الـStream الافتراضي single-subscription: مستمع واحد مدى الحياة. الاستماع مرّتين (مثلًا StreamBuilder يُعاد بناؤه) يرمي هذا الخطأ. الحلّ: .broadcast() إن كنت تحتاج عدّة مستمعين — لكن انتبه أن broadcast لا يحتفظ بالقيم للمستمعين المتأخّرين.

🎯 Senior follow-up: كيف تمنع تسريب الذاكرة مع Streams؟

كل listen() يُرجع StreamSubscription يجب cancel()ه في dispose()، وكل StreamController يجب close()ه. الاشتراك غير الملغى يبقي الـWidget حيًّا في الذاكرة ويستمرّ في استقبال الأحداث ونداء setState على عنصر مُزال — وهو سبب شائع لخطأ setState() called after dispose().

SENIORلديك ١٠ نداءات API مستقلّة. كيف تنفّذها بكفاءة؟ وماذا لو فشل أحدها؟
🎯 ماذا يختبر المُحاور؟سؤال عملي: هل تكتب await داخل حلقة (تسلسلي وبطيء) أم تعرف Future.wait؟ وهل تفكّر في الفشل الجزئي؟
// ❌ تسلسلي: 10 × 200ms = 2000ms
for (final id in ids) { results.add(await api.fetch(id)); }

// ✅ متوازٍ: ~200ms
final results = await Future.wait(ids.map(api.fetch));

// ⚠️ لكن: Future.wait تفشل كلها إن فشل واحد (fail-fast)
// للفشل الجزئي:
final settled = await Future.wait(
  ids.map((id) async {
    try   { return Ok(await api.fetch(id)); }
    catch (e) { return Err(e); }
  }),
);

🎯 Senior follow-up: ماذا لو كانت ١٠٠٠ نداء؟

Future.wait على ١٠٠٠ يفتح ١٠٠٠ اتصالًا دفعةً واحدة — فتخنق الشبكة وقد يردّ الخادم بـ429. الحلّ الصحيح تحديد التزامن (concurrency limiting): نفّذ على دفعات من ٥–١٠، أو استخدم مجموعة عمّال (worker pool). الإجابة القوية تذكر أيضًا: مهلة لكل نداء، وإعادة محاولة بتراجع أسّي (exponential backoff)، واحترام Retry-After.

🌍 Real World

هذا سؤال متكرّر جدًّا لأنه يظهر في كل تطبيق حقيقي: شاشة تعرض قائمة وتحتاج تفاصيل كل عنصر. الحلّ الأفضل غالبًا ليس التوازي أصلًا — بل تعديل الـAPI ليعيد الكل في نداء واحد (batch endpoint). ذكر هذا الخيار يُظهر أنك تفكّر كمهندس نظام لا كمستهلك API.

04Rendering Pipeline

من الـWidget إلى البكسل — قسم Senior بامتياز، ومصدر كل أسئلة الأداء.

SENIORاشرح مسار الرسم (Rendering Pipeline) من Widget إلى الشاشة.
🎯 ماذا يختبر المُحاور؟هل تستطيع تحديد أي مرحلة تسبّب مشكلة أداء؟ من لا يعرف المراحل لا يستطيع تشخيص jank إلا بالتخمين.
  Widget          الوصف — ما الذي أريده؟
     ↓
  Build           تنفيذ build() وبناء/تحديث شجرة الـElements
     ↓
  Layout          كل RenderObject: كم حجمي؟ أين أطفالي؟
     ↓             (قيود تنزل ↓ · أحجام تصعد ↑ — مرور واحد)

🧠 قاعدة Layout في Flutter — تُسأل كثيرًا

القيود تنزل، الأحجام تصعد، الأب يحدّد الموضع. (Constraints go down, sizes go up, parent sets position.) هذا يجعل الـlayout في مرور واحد O(n) — لا حلقات تفاوض بين الأب والابن كما في بعض محرّكات الويب. وهو سبب رئيسي لسرعة Flutter، وسبب أن Widget لا يستطيع معرفة حجمه أثناء build (تحتاج LayoutBuilder).

🎯 Senior follow-up: rebuild ≠ relayout ≠ repaint

العمليةماذا يحدثالتكلفة
Rebuildتنفيذ build() وإنتاج widgets جديدةرخيصة نسبيًّا
Relayoutإعادة حساب الأحجام والمواضعمتوسطة إلى عالية
Repaintإعادة توليد أوامر الرسممتوسطة
Re-rasterizeإعادة توليد البكسلات على الـGPUالأعلى

المفتاح: rebuild لا يعني بالضرورة relayout. لو أنتج build widget بنفس النوع ونفس القيود ونفس الحجم، فقد يتوقّف الأمر عند التحديث دون إعادة تخطيط أو رسم. ولهذا قد يُعاد بناء تطبيق Flutter كثيرًا دون أن يكون بطيئًا — وهي إجابة سؤال Senior شائع جدًّا.

SENIORما هو الـjank؟ وما علاقة الـ16ms؟ وكيف تشخّصه؟
🎯 ماذا يختبر المُحاور؟هل تشخّص بالأدوات أم تخمّن؟ الإجابة القوية تذكر خيطين مختلفين وتفرّق بينهما.

عند 60fps لديك 16.67ms لكل إطار (وعند 120fps فقط 8.3ms). تجاوز هذه الميزانية = إطار ضائع = ارتجاف مرئي (jank). 

ميزانية الإطار الواحدة موزّعة على خيطين:

  UI Thread          build + layout + paint  (كود Dart الخاص بك)
  Raster Thread      rasterization           (تحويل الطبقات لبكسلات)

  تجاوز أيّهما ⟹ jank — لكن العلاج مختلف تمامًا:
    UI بطيء     ← عمل ثقيل في build أو layout   → قلّل/انقل إلى Isolate
    Raster بطيء ← تأثيرات مكلفة                 → قلّل shadows/blur/opacity/clip

خطوات التشخيص بالترتيب

  1. شغّل في profile mode لا debug — debug أبطأ بأضعاف وقياساته مضلّلة تمامًا.
  2. افتح DevTools → Performance وسجّل أثناء التفاعل البطيء.
  3. حدّد الأشرطة الحمراء: أي خيط تجاوز الميزانية؟
  4. لو UI: افحص Track Widget Rebuilds — من يُعاد بناؤه بلا داعٍ؟
  5. لو Raster: فعّل Highlight repaints وHighlight oversized images.
  6. غيّر شيئًا واحدًا ثمّ أعد القياس.

🌍 Real World: أشهر ثلاثة أسباب في تطبيقات حقيقية

  • صور بلا تحجيم — صورة 4000px تُرسم في 100px تستهلك ذاكرة GPU هائلة. الحلّ: cacheWidth/cacheHeight أو ResizeImage.
  • Opacity وClipRRect في قائمة — قد تفرض طبقة (offscreen buffer) لكل عنصر. البدائل الأرخص: Color.withOpacity مباشرة، أو borderRadius على الـdecoration بدل قصّ.
  • ListView(children: [...]) بدل .builder — يبني كل العناصر دفعةً واحدة.

ماذا يحدث فعلًا بعد setState — وأشهر سؤال Senior عن Keys.

🎯 ماذا يختبر المُحاور؟سؤال مصيدة مزدوج: كثيرون يقولون «يُعاد بناء الشاشة كلها» (مبالغة) أو «يُعاد رسم كل شيء» (خلط بين rebuild وrepaint).

🎯 Senior follow-up: لماذا setState غير متزامن في أثره؟

لأنه لا يبني شيئًا — بل يسم ويجدول. لو استدعيته عشر مرّات في دالّة واحدة، فلن يحدث إلا build واحد في الإطار التالي (batching). ولهذا أيضًا استدعاؤه أثناء build خطأ يرمي استثناءً: أنت تعدّل الشجرة أثناء بنائها.

SENIORما هي الـKeys؟ ومتى تحتاجها فعلًا؟ اشرح الفرق بين أنواعها.
🎯 ماذا يختبر المُحاور؟سؤال Senior كلاسيكي. الإجابة الضعيفة: «تُستخدم في القوائم». الإجابة القوية تشرح مشكلة الهوية (identity) في المطابقة بسيناريو ملموس.

عند المطابقة، يقارن Flutter الـWidget القديم بالجديد في الموقع نفسه: canUpdate = runtimeType متطابق && key متطابق. بلا key، يعتمد التمييز على الموقع فقط — وهنا تقع المشكلة.

🌍 السيناريو الذي يكشف المشكلة

قائمة من StatefulWidget لكل منها عدّاد داخلي. تحذف العنصر الأول. بلا keys: الـElement في الموقع صفر يرى widget من نفس النوع، فيقول «نفس الشيء» ويُبقي حالته — فيظهر عدّاد العنصر المحذوف على العنصر الذي يليه. الحالة التصقت بالموقع لا بالبيانات. 

// ❌ الحالة تلتصق بالموقع
items.map((i) => TodoTile(item: i)).toList()

// ✅ الحالة تتبع البيانات
items.map((i) => TodoTile(key: ValueKey(i.id), item: i)).toList()
النوعيقارن بـاستخدمه حين

UniqueKey()لا شيء — فريد دائمًاحين تريد إجبار إعادة الإنشاء

⚠️ Interview Trap: UniqueKey() داخل build

key: UniqueKey() يُنشئ مفتاحًا جديدًا في كل build، فيفشل canUpdate دائمًا، فيُدمَّر الـElement والـState ويُعاد إنشاؤهما في كل إطار. النتيجة: فقدان الحالة، انقطاع الأنيميشن، وأداء كارثي. و GlobalKey مكلف أيضًا — لا تستخدمه لمجرّد تمييز عناصر قائمة.

حين يسأل المُحاور «أي state management تفضّل؟» فهو لا يسأل عن مكتبة. يسأل: هل تفهم أن «الحالة» ليست شيئًا واحدًا؟ الإجابة التي تبدأ بـ«Riverpod أفضل من Provider» تُصنّفك فورًا كمرشّح Mid. الإجابة القوية تبدأ بـ«أي نوع من الحالة؟».

MID-LEVELما المشكلة التي تحلّها إدارة الحالة أصلًا؟ وما أنواع الحالة؟
🎯 ماذا يختبر المُحاور؟هل تستطيع تصنيف الحالة قبل اختيار الأداة؟ هذا التصنيف وحده يرفع مستوى إجابتك درجة كاملة.

المشكلة: بيانات يحتاجها أكثر من widget، في مواضع متباعدة من الشجرة، ويجب أن تبقى مصدرًا واحدًا للحقيقة وأن تنعكس تغييراتها على الواجهة تلقائيًّا. بلا حلّ منظّم تنتهي إلى prop drilling — تمرير البيانات عبر عشر طبقات — أو إلى نسخ متعارضة من الحقيقة.

🧠 Server State ليس مثل بقية الحالة — وهذا يستحقّ الذكر

حالة الخادم ليست ملكك: لها نسخة أصلية في مكان آخر، وتتقادم، وتحتاج إعادة جلب وإبطال cache وحالات تحميل/خطأ. معاملتها كمتغيّر عادي هي أصل معظم أخطاء المزامنة. ذكر هذا التمييز يُظهر أنك بنيت تطبيقات حقيقية.

BEGINNERمتى يكفي setState؟ ومتى يصير خطأً؟
🎯 ماذا يختبر المُحاور؟هل تُفرط في الهندسة؟ من يقول «لا أستخدم setState أبدًا، أستخدم Bloc دائمًا» يُظهر انعدام حكم لا خبرة.

setState صحيح تمامًا حين: الحالة تخصّ widget واحدًا، ولا يحتاجها أحد آخر، وتموت بموته. مؤشّر تحميل زر، فتح/إغلاق قائمة منسدلة، تبويب مختار محلّيًّا.

يصير خطأً حين: بدأت ترفعه لأعلى وأعلى لتشاركه (lifting state up المتسلسل)، أو صرت تمرّر callbacks عبر ٣+ طبقات، أو احتاجت الحالة أن تنجو من إزالة الشاشة.

🎯 صياغة قوية للمقابلة

«أبدأ بـsetState افتراضيًّا وأرفع الحالة فقط حين يفرض عليّ متطلَّب حقيقي ذلك — مشاركة بين شاشتين، أو بقاء بعد التنقّل. إدخال مكتبة إدارة حالة لحالة محلّية يضيف تعقيدًا واختبارات ومفاهيم بلا مقابل.»

MID-LEVELما هو InheritedWidget؟ ولماذا بُنيت عليه معظم المكتبات؟
🎯 ماذا يختبر المُحاور؟هل تعرف الآلية الأصلية في Flutter نفسه، أم تعرف المكتبات فقط؟

InheritedWidget هو الآلية المدمجة لتمرير البيانات لأسفل الشجرة بوصول O(1)، وإخطار المعتمدين عند التغيّر. Theme وMediaQuery وNavigator كلها كذلك. 

class UserScope extends InheritedWidget {
  const UserScope({required this.user, required super.child});
  final User user;

  static User of(BuildContext c) =>
      c.dependOnInheritedWidgetOfExactType<UserScope>()!.user;
      // ↑ يسجّل الـElement كمعتمد ⟹ يُعاد بناؤه عند التغيّر

  @override
  bool updateShouldNotify(UserScope old) => old.user != user;   // ← التحكّم في الإخطار
}

🎯 Senior follow-up: لماذا لا نستخدمه مباشرة إذًا؟

لأنه يوفّر القراءة فقط — لا يحلّ: كيف تُحدَّث القيمة، ولا دورة حياة الموارد (متى تُنشأ وتُتلَف)، ولا حقن الاعتماديات، ولا الحالة غير المتزامنة، ولا الاعتماد بين مزوّدات. Provider وRiverpod يبنيان فوقه ليحلّا هذه بالضبط.

نقطة دقيقة تُثير إعجاب المُحاور: dependOnInheritedWidgetOfExactType يُخطر كل المعتمدين عند أي تغيّر. لتحديث جزئي دقيق تحتاج InheritedModel أو آلية select في المكتبات.

🎯 الإجابة النموذجية

«لا يوجد أفضل مطلق — يوجد أنسب للسياق. لفريق كبير بتدفّقات معقّدة يحتاج سجلّ أحداث قابلًا للتتبّع، صرامة Bloc ميزة لأنها تفرض الانضباط. لتطبيق يغلب عليه التعامل مع حالة الخادم، Riverpod يعطيني AsyncValue و autoDispose وfamily جاهزة فأكتب أقلّ. ولتطبيق صغير قد يكفي setState وInheritedWidget بلا أي مكتبة.

وما يهمّني أكثر من الاسم: أن يكون هناك مصدر واحد للحقيقة، وتدفّق بيانات أحادي الاتجاه، وأن تكون الحالة قابلة للاختبار بمعزل عن الواجهة. هذه الخصائص أهمّ من المكتبة التي توفّرها.» 

Unidirectional Data Flow — المبدأ الذي يهمّ أكثر من الأداة:

  User Action  ──→  State Change  ──→  UI Rebuild  ──→  User sees result
       ↑                                                        │
       └────────────────────────────────────────────────────────┘

الواجهة لا تعدّل الحالة مباشرة — ترسل نيّة، والحالة تتغيّر، فتُشتقّ الواجهة منها.

07Riverpod

مطلوب في أغلب إعلانات Flutter الحديثة — وهذه أسئلته المتكرّرة.

MID-LEVELما أنواع المزوّدات في Riverpod ومتى تستخدم كلًّا منها؟
🎯 ماذا يختبر المُحاور؟هل تختار النوع بناءً على «هل توجد حالة قابلة للتغيير؟ وهل هي غير متزامنة؟» — أم تستخدم واحدًا لكل شيء؟

@riverpod
class Todos extends _$Todos {
  @override
  Future<List<Todo>> build() async => ref.watch(repoProvider).fetchAll();

  Future<void> add(Todo t) async {
    state = const AsyncLoading();
    state = await AsyncValue.guard(() async {      // ← يلتقط الخطأ تلقائيًّا
      await ref.read(repoProvider).add(t);
      return ref.read(repoProvider).fetchAll();
    });
  }
}

🎯 Senior follow-up: FutureProvider أم AsyncNotifier؟

القاعدة: FutureProvider للقراءة فقط — «اجلب واعرض». AsyncNotifier حين تحتاج دوالّ تعدّل الحالة (إضافة/حذف/تحديث متفائل). لا يمكنك تعديل حالة FutureProvider من الخارج، فلو احتجت ذلك فأنت تستخدم النوع الخطأ.

SENIORما فائدة .family و .autoDispose؟ وما خطرهما؟
🎯 ماذا يختبر المُحاور؟هل تفهم دورة حياة المزوّد — وهي مصدر شائع لتسريبات الذاكرة وأخطاء «البيانات القديمة»؟
// family: مزوّد مُعامَل — نسخة مستقلّة لكل وسيط

    ref.watch(repoProvider).fetch(id);

class Session extends _$Session { ... }

⚠️ Interview Trap: family بلا autoDispose

كل وسيط جديد يُنشئ مزوّدًا يبقى في الذاكرة إلى الأبد. تصفّح ١٠٠٠ منتج ⟹ ١٠٠٠ مزوّد حيّ ⟹ تسريب حقيقي. القاعدة: family يجب أن تكون autoDispose إلا لسبب صريح.

والوجه الآخر: autoDispose يتلف الحالة فور اختفاء آخر مستمع — فلو خرج المستخدم من الشاشة وعاد، أُعيد الجلب. إن أردت الاحتفاظ مؤقّتًا استخدم ref.keepAlive() مشروطًا، أو Timer للإبقاء لفترة.

SENIORكيف تختبر مزوّد Riverpod؟ وكيف تستبدل الاعتماديات؟
🎯 ماذا يختبر المُحاور؟هذا سؤال يجمع الاختبار وحقن الاعتماديات — وهو أقوى ما في Riverpod فعلًا.
test('يُرجع المستخدمين من الـrepository', () async {
  final container = ProviderContainer(
    overrides: [
      repoProvider.overrideWithValue(FakeRepo()),   // ← DI بلا واجهة مجرّدة
    ],
  );
  addTearDown(container.dispose);                   // ← لا تنسَ

  final users = await container.read(usersProvider.future);
  expect(users, hasLength(2));
});

🎯 Senior insight: هذا يُلغي حجّة «Repository مجرّد للاختبار»

الحجّة التقليدية لـabstract class Repository هي «حتى أزيّفه في الاختبار». لكن overrideWithValue يستبدل الصنف الفعلي دون أي واجهة. فتبقى فائدة واحدة للتجريد: استبدال التنفيذ في الإنتاج — وهو سيناريو نادر في تطبيقات الموبايل.

قولها في مقابلة يُظهر أنك تقيّم الأنماط بفائدتها لا بشهرتها: «أضيف تجريدًا حين يشتري لي شيئًا لا أملكه أصلًا.»

🌍 Real World: AsyncValue ولماذا هو مفيد

ref.watch(usersProvider).when(
  data:    (users) => UserList(users),
  loading: () => const Loader(),
  error:   (e, st) => ErrorView(e),
);

يفرض عليك التعامل مع الحالات الثلاث — فلا تنسى حالة الخطأ كما يحدث كثيرًا مع Future الخام. ولديه أيضًا valueOrNull وisLoading للحالات المركّبة مثل «أعرض البيانات القديمة أثناء التحديث».

08Architecture

المعمارية ليست مجلّدات — هي حدود ومسؤوليات واتجاه اعتماد.

SENIORما هي Clean Architecture؟ ومتى لا تستخدمها؟
🎯 ماذا يختبر المُحاور؟هذا أشهر سؤال معماري وأكثره إجابات محفوظة. من يقول «ثلاث مجلّدات: data وdomain وpresentation» يُصنَّف فورًا كمن قرأ مقالًا. الجوهر كلمتان: Dependency Rule.
  Presentation  ──────→  Domain  ←──────  Data
   (UI · State)          (Entities        (Repositories Impl
                          UseCases         DataSources · DTOs)
                          Repo Interfaces)

  اتجاه الاعتماد:  دائمًا نحو الداخل ↓
  الطبقة الداخلية (Domain) لا تعرف شيئًا عن الخارج:
  لا Flutter · لا Dio · لا JSON · لا قاعدة بيانات.

  Dependency Inversion: الـDomain يعرّف العقد (abstract)،
  والـData ينفّذه ⟹ الاعتماد ينعكس نحو الداخل.

🧠 ما الذي تشتريه فعلًا؟

  • قابلية الاختبار — منطق الأعمال يُختبر بلا Flutter ولا شبكة.
  • قابلية الاستبدال — تغيير REST إلى GraphQL يلمس طبقة Data وحدها.
  • استقلال عن الإطار — الـDomain ينجو من ترقية أو تغيير المكتبات.

⚠️ ومتى تكون خطأً؟ — الجزء الذي ينساه الجميع

حين تدفع الثمن بلا أن تقبض المقابل. تطبيق CRUD بسيط بمصدر بيانات واحد لا نيّة لاستبداله: كل قراءة تصير خمسة ملفات (Entity · Model · Repo interface · Repo impl · UseCase) لتُرجع الحقل نفسه. هذا يُبطئ الفريق مقابل مرونة لن تُستعمل.

وخطأ شائع آخر: وضع نموذج فيه fromJson() داخل domain/entities/. إن كان يعرف JSON فهو DTO لا Entity — والمجلّد لا يصنع الطبقة، الاعتماديات هي التي تصنعها.

🎯 الإجابة النموذجية الكاملة

«Clean Architecture ليست بنية مجلّدات بل قاعدة اتجاه اعتماد: الاعتماد يشير للداخل دائمًا، ومنطق الأعمال لا يعرف الإطار ولا مصدر البيانات. أشتري بها قابلية الاختبار والاستبدال، وأدفع مقابلها ملفات أكثر وقفزات أكثر عند القراءة.

أطبّقها كاملة حين يكون منطق الأعمال غنيًّا أو يعمل الفريق على وحدات متوازية. ولتطبيق بسيط أكتفي بحدّ أدنى لا أتنازل عنه: الـWidget لا ينادي الشبكة مباشرة أبدًا، وطبقة واحدة تعرف الـAPI. هذا يحقّق ٨٠٪ من الفائدة بـ٢٠٪ من التكلفة، وأضيف UseCases لاحقًا حين يظهر منطق يستحقّها.»

MID-LEVELما هو Repository Pattern؟ ومتى يصير تجريدًا زائدًا؟
🎯 ماذا يختبر المُحاور؟هل تستطيع نقد نمط شائع؟ القدرة على قول «هذا النمط لا يلزم هنا» علامة نضج قوية.

Repository يفصل «ماذا أريد من البيانات» عن «من أين تأتي». الواجهة تطلب getUser(id) ولا تعرف أشبكةٌ هي أم cache أم قاعدة محلّية. 

class UserRepository {
  UserRepository(this._remote, this._local);
  final RemoteDataSource _remote;
  final LocalDataSource  _local;

  Future<User> getUser(int id) async {
    final cached = await _local.get(id);
    if (cached != null && !cached.isStale) return cached;   // ← القرار هنا
    final fresh = await _remote.fetch(id);
    await _local.save(fresh);
    return fresh;
  }
}

🎯 متى يصير زائدًا؟

حين يكون مجرّد تمرير: getUser(id) => api.getUser(id) بلا cache ولا دمج مصادر ولا تحويل. عندها أضفت ملفًّا وواجهة وطبقة قفز مقابل صفر منطق. Repository يستحقّ وجوده حين يتّخذ قرارًا — أي حين يوجد أكثر من مصدر، أو cache، أو تحويل DTO→Domain، أو دمج نداءات.

والوجه المقابل الذي يجب ذكره للتوازن: حتى لو كان تمريرًا اليوم، فوجوده يعني أن إضافة الـcache غدًا تلمس ملفًّا واحدًا. القرار يعتمد على احتمال حدوث ذلك فعلًا — وهذا حكم لا قاعدة.

🎯 القاعدة الحقيقية: اتجاه الاعتماد لا اسم المجلّد

Feature-first تتفوّق مع النموّ، لكن الفائدة تتبخّر إن استوردت الميزات بعضها عشوائيًّا. الانضباط الذي يجب ذكره:

  • features → core دائمًا، والعكس ممنوع.
  • الميزات لا تستورد بعضها — وإلا عاد التشابك الذي هربت منه.
  • ما تحتاجه ميزتان يصعد إلى core أو إلى وحدة مجال مشتركة.
  • المشترك يصعد عند ظهور المستهلك الثاني فعلًا، لا توقّعًا له.

نقطة تُنهي الإجابة بقوّة: «المُصرِّف لا يفرض هذه القواعد — استيراد مخالف يُصرَّف وينجح ويمرّ الاختبارات. لذلك أضيف فحصًا في CI يكسر البناء عند المخالفة، وإلا انحدرت البنية بصمت.»

09SOLID

خمسة مبادئ — لكل منها سؤال «أرِني مثالًا سيّئًا ثم أصلحه».

MID-LEVELS — Single Responsibility: اشرحه بمثال Flutter.
🎯 ماذا يختبر المُحاور؟التعريف الشائع «الصنف يفعل شيئًا واحدًا» ضبابي. التعريف الدقيق: سبب واحد للتغيير — أي جهة واحدة تطلب تعديله.

MID-LEVELO · L · I — اشرح الثلاثة الأوسط بأمثلة.
🎯 ماذا يختبر المُحاور؟عادةً يُسأل عن واحد منها فقط — لكن Liskov هو الأصعب وأكثرها كشفًا لعمق الفهم.

O — Open/Closed: مفتوح للامتداد، مغلق للتعديل

// ❌ كل نوع دفع جديد يفرض تعديل هذه الدالّة
double fee(String type) {
  if (type == 'card')  return 2.5;
  if (type == 'apple') return 1.5;
  return 0;                                  // ← تعديل متكرّر = خطر انحدار
}

// ✅ الامتداد بإضافة صنف لا بتعديل قائم
abstract class PaymentMethod { double get fee; }
class CardPayment  implements PaymentMethod { double get fee => 2.5; }
class ApplePay     implements PaymentMethod { double get fee => 1.5; }

L — Liskov Substitution: البديل لا يكسر التوقّعات

// ❌ خرق واضح: النوع الفرعي يضيّق العقد
class Bird          { void fly() => ...; }
class Penguin extends Bird {
  void fly() => throw UnsupportedError('لا يطير');   // ← كسر التوقّع
}
// كل كود يتعامل مع Bird سينهار عند تمرير Penguin

// ✅ نمذجة القدرات لا التصنيف البيولوجي
abstract class Bird       { void eat(); }
abstract class FlyingBird extends Bird { void fly(); }

القاعدة العملية: النوع الفرعي يجوز أن يوسّع العقد، ولا يجوز أن يضيّقه — لا يرمي استثناءات جديدة، ولا يشدّد الشروط المسبقة، ولا يُضعف الضمانات.

I — Interface Segregation: واجهات صغيرة مركّزة

// ❌ واجهة سمينة تُجبر المنفّذ على دوالّ لا تعنيه

class ReadOnlyCache implements DataSource {

}

SENIORD — Dependency Inversion: ما الفرق بينه وبين Dependency Injection؟
🎯 ماذا يختبر المُحاور؟سؤال يفصل من فهم المبدأ عمّن حفظ الاختصار. كثيرون يخلطونهما تمامًا.
Dependency Injection (DI)      = تقنية: مرّر الاعتمادية من الخارج
Dependency Inversion (DIP)     = مبدأ: اعتمد على تجريد لا على تنفيذ

يمكن أن تطبّق DI بلا DIP:
  UserService(DioClient client)          ← حُقنت، لكنها نوع ملموس

DIP الكامل:
  UserService(HttpClient client)          ← تعتمد على تجريد
  والـDomain هو من يعرّف HttpClient لا طبقة البنية التحتية
// ❌ الطبقة العليا تعتمد على تفصيل تقني
class UserService {
  final dio = Dio();                       // تصنع اعتماديتها + نوع ملموس
  Future<User> get(int id) async => ...;   // اختبارها يحتاج شبكة حقيقية
}

// ✅ الطبقة العليا تعرّف العقد، والتفصيل ينفّذه
abstract class UserGateway { Future<User> get(int id); }   // في الـDomain

class DioUserGateway implements UserGateway { ... }        // في الـData
class FakeUserGateway implements UserGateway { ... }       // في الاختبار

class UserService {
  UserService(this._gateway);
  final UserGateway _gateway;              // ← الاعتماد انعكس نحو الداخل
}

🎯 Senior follow-up: متى DIP غير مبرَّر؟

حين لا يوجد أكثر من تنفيذ ولا نيّة لذلك، وحين تملك أداة تزييف بلا تجريد. في Riverpod مثلًا يستبدل overrideWithValue الصنف الملموس في الاختبار — فتسقط الحجّة الوحيدة المتبقّية. إجابة ناضجة: «أطبّق DIP حين يشتري لي شيئًا: تنفيذ ثانٍ حقيقي، أو حدّ معماري أريد حمايته، أو اختبار لا أستطيعه بغيره.»

لأن الشبكة على الموبايل غير موثوقة: قد ينجح الطلب ويضيع الردّ، فيعيد العميل المحاولة. لو كان الطلب POST دفع، دفع المستخدم مرّتين. الحلّ: مفتاح فريد لكل عملية يرسله العميل، والخادم يتجاهل التكرار. ذكر هذا في مقابلة موبايل يُظهر خبرة ميدانية حقيقية.

SENIORكيف تصمّم API Client في Flutter؟ ولماذا لا ينادي الـWidget طبقة الشبكة مباشرة؟
🎯 ماذا يختبر المُحاور؟سؤال معماري مقنّع في صيغة تقنية. يريد أن يسمع حدودًا ومسؤوليات، لا اسم مكتبة.

     ↓

لماذا لا ينادي الـWidget dio.get() مباشرة؟ خمسة أسباب محدّدة

  1. الاختبار — اختبار الـWidget يصير محتاجًا شبكة حقيقية.
  2. التكرار — معالجة الأخطاء والمهلة تتكرّر في كل شاشة وتتباين.
  3. الاقتران — تغيير شكل الردّ يفرض تعديل كل شاشة تستهلكه.
  4. لا مكان مشترك للـheaders والتسجيل والقياس وإعادة المحاولة.

class ApiClient {
  ApiClient(this._dio);
  final Dio _dio;

  Future<T> get<T>(String path, T Function(Map<String, dynamic>) parse) async {
    try {
      final res = await _dio.get(path);
      return parse(res.data);
    } on DioException catch (e) {
      throw _mapError(e);            // ← نقطة واحدة تحوّل أخطاء النقل إلى أخطاء مجال
    }
  }
}

🎯 Senior insight: Interceptors هي Decorator Pattern

إضافة الـtoken، والتسجيل، وإعادة المحاولة، وقياس الزمن — كلها اهتمامات عرضية (cross-cutting) توضع في interceptors بدل تكرارها في كل نداء. هذا يجعل ApiClient نظيفًا ويجعل تلك السلوكيات قابلة للتشغيل والإطفاء والاختبار مستقلّةً.

SENIORكيف تتعامل مع تجديد الـtoken حين تفشل ٥ طلبات متزامنة بـ401؟
🎯 ماذا يختبر المُحاور؟سؤال Senior ممتاز لأنه يبدو بسيطًا وفيه مشكلة تزامن حقيقية. الإجابة الساذجة تُنتج ٥ عمليات تجديد متوازية.
❌ الساذج:                        ✅ الصحيح:
5 طلبات → 5 × 401                5 طلبات → 5 × 401
→ 5 عمليات تجديد متوازية          → أول 401 يبدأ التجديد
→ الخادم قد يُبطل الـtokens        → البقية تنتظر نفس الـFuture
→ سباق: من يكتب الأخير؟           → عند النجاح: تُعاد كلها بالـtoken الجديد
class AuthInterceptor extends Interceptor {
  Future<String>? _refreshing;              // ← المفتاح: Future واحد مشترك

  @override
  Future<void> onError(DioException e, ErrorInterceptorHandler handler) async {
    if (e.response?.statusCode != 401) return handler.next(e);

    try {
      // كل الطلبات المتزامنة تنتظر نفس العملية
      final token = await (_refreshing ??= _doRefresh());
      final res = await _retry(e.requestOptions, token);
      return handler.resolve(res);
    } catch (_) {
      await _logout();                       // ← فشل التجديد: اخرج
      return handler.next(e);
    } finally {
      _refreshing = null;                    // ← أفرغ للمرّة القادمة
    }
  }
}

🎯 أسئلة المتابعة المؤكّدة — جهّز إجاباتها

  • وماذا لو فشل الـrefresh token نفسه؟ تسجيل خروج نظيف: امسح التخزين الآمن، أبطل الطلبات المعلّقة، وجّه لشاشة الدخول مرّة واحدة لا خمس مرّات.
  • وأين تخزّن الـtokens؟ flutter_secure_storage (Keychain/Keystore) — لا SharedPreferences.
  • وكيف تمنع حلقة لا نهائية؟ علّم الطلب المُعاد بعلامة؛ لو عاد 401 ثانيةً لا تجدّد مرّة أخرى.
  • ولو انتهت الصلاحية أثناء التجديد؟ Refresh token rotation + التعامل مع سباق التدوير على الخادم.

MID-LEVELكيف تنمذج الأخطاء في تطبيق Flutter؟
🎯 ماذا يختبر المُحاور؟هل تحوّل أخطاء البنية التحتية إلى أخطاء مجال؟ تسريب DioException إلى الواجهة رائحة معمارية واضحة.

  const AppFailure(this.message);
  final String message;
}
class NetworkFailure    extends AppFailure { ... }  // لا اتصال · مهلة

class ValidationFailure extends AppFailure { final Map<String, String> fields; }
class AuthFailure       extends AppFailure { ... }  // 401/403
class ParsingFailure    extends AppFailure { ... }  // شكل غير متوقّع
class UnknownFailure    extends AppFailure { ... }

// sealed ⟹ switch مكتمل يفرضه المُصرِّف
String userMessage(AppFailure f) => switch (f) {
  NetworkFailure()    => 'تحقّق من اتصالك بالإنترنت',
  AuthFailure()       => 'انتهت الجلسة، سجّل الدخول مجدّدًا',
  ValidationFailure() => 'راجع البيانات المُدخلة',

};

🧠 مبدأ: حوّل الأخطاء عند حدود الطبقات

DioException تفصيل نقل. الواجهة يجب ألّا تعرفه. طبقة ApiClient تحوّله إلى AppFailure، فيصير تبديل Dio بـhttp غير مؤثّر على أي شاشة. وهذا هو الاختبار العملي لجودة حدودك المعمارية.

🎯 Senior: Exceptions أم Result type؟

Result<T, E> (أو Either) يجعل الفشل ظاهرًا في التوقيع فلا يمكن نسيانه — المُصرِّف يفرض التعامل معه. الثمن: قالبية أكثر ومكتبة إضافية غالبًا.

موقف متوازن يُعجب المُحاورين: «أستخدم Result للفشل المتوقّع الذي يغيّر الواجهة (فشل تسجيل الدخول، خطأ تحقّق)، والاستثناءات للفشل الاستثنائي فعلًا. استخدام Result لكل شيء يحوّل الكود إلى سلسلة fold متداخلة تقلّل القراءة أكثر ممّا تزيد الأمان.»

🌍 بقيّة أسئلة الأمان المتوقّعة

  • أين تخزّن الـtokens؟ flutter_secure_storage → Keychain (iOS) / Keystore (Android). ليس SharedPreferences — نصّ صريح يُقرأ على جهاز مكسور الحماية.
  • Certificate pinning؟ يمنع اعتراض MITM بشهادة مزوّرة. الثمن: انتهاء صلاحية الشهادة يعطّل التطبيق حتى تحديثه — لذلك ثبّت على المُصدِر (CA) أو المفتاح العام لا الشهادة نفسها، واحتفظ بنسخة احتياطية.
  • Authentication vs Authorization؟ Authentication = من أنت (401). Authorization = ماذا يحقّ لك (403). خلطهما فخّ شائع.
  • التسجيل: لا تسجّل tokens ولا كلمات مرور ولا بيانات شخصية — سجلّات الإنتاج تُقرأ من كثيرين.
  • التحقّق من المدخلات: تحقّق العميل للتجربة، وتحقّق الخادم للأمان. لا تثق بالعميل أبدًا.

🎯 الإجابة الناضجة

«أبدأ بـmonolith منظّم بوحدات واضحة. Microservices تحلّ مشكلة تنظيمية أساسًا — فرق تتعثّر ببعضها — وتشتري ذلك بثمن باهظ: شبكة بين كل نداءين، تصحيح موزّع، اتّساق نهائي، وتعقيد نشر. لو كان الفريق صغيرًا فأنت تدفع الثمن كاملًا بلا مقابل. وحين ينفصل جزء بحدّ واضح ويحتاج توسّعًا مختلفًا، أستخرجه وحده.»

Event-Driven: الخدمات تتواصل بأحداث عبر وسيط (Kafka/RabbitMQ) بدل نداءات مباشرة. المكسب: فكّ ارتباط وقابلية توسّع ومرونة أمام الفشل. الثمن: اتّساق نهائي، وترتيب غير مضمون، وضرورة أن تكون المعالجات قابلة لإعادة التنفيذ (idempotent) لأن التسليم قد يتكرّر.

for (final o in allOrders) { byUser.putIfAbsent(o.userId, () => []).add(o); }
for (final u in users) { final orders = byUser[u.id] ?? const []; }   // O(1)

لماذا تهمّ في الموبايل خصوصًا؟ لأن ميزانيتك 16ms وليست ثانية كاملة كما في خادم، والمعالج أضعف، والبطارية محدودة. حلقة O(n²) داخل build تعني إطارًا ضائعًا مضمونًا.

19LLM APIs وأساسيات الدمج

ما يجب أن يعرفه مهندس موبايل يدمج الذكاء الاصطناعي — لا ما يعرفه باحث ML.

🧠 ما الذي يُختبر في دور AI Integration فعلًا؟

لن يُسألوك عن تدريب نموذج أو رياضيات Transformers. يُسألون عن الهندسة حول النموذج: أين يعيش المفتاح؟ كيف تتعامل مع زمن استجابة ٣ ثوانٍ؟ كيف تضبط التكلفة؟ ماذا يحدث حين يهلوس النموذج أو تسقط الخدمة؟ كيف تقيس أن النظام جيد؟ النموذج مكوّن غير موثوق وبطيء ومكلف في نظامك — وهذه هندسة أنظمة لا ML.

// الخدمة: تحويل الاستجابة المتدفّقة إلى Stream<String>
Stream<String> streamChat(String message) async* {
  final req = http.Request('POST', uri)
    ..headers['Authorization'] = 'Bearer $userToken'
    ..body = jsonEncode({'message': message});

  final res = await http.Client().send(req);
  if (res.statusCode != 200) throw ServerFailure(res.statusCode);

  await for (final chunk in res.stream.transform(utf8.decoder)) {
    for (final line in chunk.split('\n')) {
      if (!line.startsWith('data: ')) continue;
      final data = line.substring(6);
      if (data == '[DONE]') return;
      yield jsonDecode(data)['delta'] as String;      // ← جزء من النصّ
    }
  }
}

// الحالة: تجميع تدريجي
Future<void> send(String text) async {
  state = state.addUser(text).addEmptyAssistant();
  final buf = StringBuffer();
  try {
    await for (final delta in _repo.streamChat(text)) {
      buf.write(delta);
      state = state.updateLastAssistant(buf.toString());   // ← إعادة بناء تدريجية
    }
  } catch (e) {
    state = state.updateLastAssistant('${buf.toString()}\n\n⚠️ انقطع الاتصال');
  }
}

🎯 Senior follow-up: تحدّيات لا يذكرها المرشّح المتوسّط

  • أجزاء غير مكتملة — قد يصل نصف سطر SSE؛ احتفظ ببفر وحلّل الأسطر الكاملة فقط.
  • الأداء — setState لكل token يعني عشرات إعادات البناء في الثانية. اجمعها (batching) كل ~٥٠ms أو استخدم ValueNotifier للفقاعة الأخيرة وحدها.
  • الإلغاء — المستخدم غادر الشاشة؟ ألغِ الاشتراك وأبلغ الخادم ليوقف التوليد — وإلا دفعت مقابل tokens لن يراها أحد.
  • Markdown جزئي — قد يصل **نص بلا إغلاق؛ اعرض نصًّا خامًا أثناء التدفّق وصيّره عند الاكتمال، أو استخدم محلّلًا متسامحًا.
  • التمرير التلقائي — انزل مع النصّ، لكن توقّف إن مرّر المستخدم لأعلى يدويًّا.
  • المهلة — مهلة على الخمول بين الأجزاء لا على الطلب كله؛ وإلا قطعت ردًّا طويلًا سليمًا.

MID-LEVELما Embeddings و Vector Search و Chunking؟
🎯 ماذا يختبر المُحاور؟الفهم الحدسي لا الرياضي. وسؤال متابعة شبه مؤكّد: لماذا لا يمكن خلط نماذج تضمين مختلفة؟

Embedding: تحويل نصّ إلى متجه أرقام (٧٦٨ أو ١٥٣٦ بُعدًا عادةً) بحيث تقع النصوص المتقاربة في المعنى قريبةً في الفضاء — حتى لو لم تشترك في أي كلمة.

🎯 القرارات التي تُميّز الإجابة

  • التصعيد ميزة أولى لا احتياطية. عرّف متى يُسلَّم لإنسان: ثقة منخفضة، مشاعر سلبية، ذكر شكوى قانونية، أو طلب المستخدم صراحةً. مساعد لا يعرف حدّه يُفقد ثقة العملاء.

  • Cache للأسئلة المتكرّرة. «كيف أُعيد تعيين كلمة المرور؟» تتكرّر آلاف المرّات — تخزينها يوفّر معظم التكلفة.

  • مسار احتياطي: سقط مزوّد الـLLM؟ نموذج بديل، أو بحث في قاعدة المعرفة يعرض المقالات مباشرةً، أو تصعيد فوري — لا صفحة خطأ.

🎯 ماذا يختبر المُحاور؟تمرين عملي جدًّا — كل تطبيق فيه بحث يحتاج debounce، وكل تطبيق يتعامل مع شبكة يحتاج retry.
class Debouncer {
  Debouncer(this.delay);
  final Duration delay;
  Timer? _timer;

  void call(void Function() action) {
    _timer?.cancel();                       // ألغِ المعلّق
    _timer = Timer(delay, action);
  }
  void dispose() => _timer?.cancel();       // ⚠️ لا تنسَ
}

Future<T> retry<T>(
  Future<T> Function() task, {
  int maxAttempts = 3,
  Duration base = const Duration(milliseconds: 300),
}) async {
  for (var attempt = 1; ; attempt++) {
    try {
      return await task();
    } catch (e) {
      if (attempt >= maxAttempts || !_isRetryable(e)) rethrow;
      // تراجع أسّي + jitter لتفادي "قطيع الرعد"
      final backoff = base * math.pow(2, attempt - 1).toDouble();
      final jitter  = Duration(milliseconds: math.Random().nextInt(200));
      await Future.delayed(backoff + jitter);
    }
  }
}

bool _isRetryable(Object e) =>
    e is SocketException || (e is HttpException) /* || 5xx || 429 */;

🎯 Senior follow-up: لماذا jitter؟ وما الفرق بين debounce و throttle؟

Jitter: لولاه، ألف عميل فشلوا في اللحظة نفسها سيعيدون المحاولة في اللحظة نفسها بالضبط — فيسقط الخادم ثانيةً (thundering herd). العشوائية توزّع الضغط.

Debounce ينتظر توقّف الأحداث ثم ينفّذ مرّة (بحث أثناء الكتابة). Throttle ينفّذ بمعدّل أقصى ثابت (تتبّع التمرير). خلطهما خطأ شائع: throttle للبحث يرسل طلبات وسط الكتابة، وdebounce للتمرير يجعله متقطّعًا.

SENIORنفّذ LRU Cache و Rate Limiter
🎯 ماذا يختبر المُحاور؟LRU سؤال كلاسيكي؛ في Dart له حلّ أنيق لأن LinkedHashMap يحفظ ترتيب الإدراج.
class LruCache<K, V> {
  LruCache(this.capacity) : assert(capacity > 0);
  final int capacity;
  final _map = <K, V>{};                    // Map في Dart = LinkedHashMap

  V? get(K key) {
    if (!_map.containsKey(key)) return null;
    final v = _map.remove(key) as V;         // احذف ثمّ أعد الإدراج
    _map[key] = v;                           // ⟹ ينتقل إلى النهاية (الأحدث)
    return v;
  }

  void put(K key, V value) {
    _map.remove(key);                        // لتحديث الترتيب لو موجود
    _map[key] = value;
    if (_map.length > capacity) {
      _map.remove(_map.keys.first);          // الأقدم استخدامًا
    }
  }
}
// get و put كلاهما O(1) بمتوسّط
/// Token bucket: يسمح بدفعات قصيرة مع حدّ معدّل ثابت
class RateLimiter {
  RateLimiter({required this.maxTokens, required this.refillPerSecond})
      : _tokens = maxTokens.toDouble(), _last = DateTime.now();

  final int maxTokens;
  final double refillPerSecond;
  double _tokens;
  DateTime _last;

  bool tryAcquire([int cost = 1]) {
    final now = DateTime.now();
    final elapsed = now.difference(_last).inMilliseconds / 1000;
    _tokens = math.min(maxTokens.toDouble(), _tokens + elapsed * refillPerSecond);
    _last = now;
    if (_tokens >= cost) { _tokens -= cost; return true; }
    return false;
  }
}

🎯 أسئلة المتابعة

  • LRU آمن للخيوط؟ في isolate واحد لا حاجة لأقفال. عبر isolates لا تُشارَك الذاكرة أصلًا — تحتاج تصميمًا مختلفًا (رسائل أو تخزين مشترك).
  • LRU مع انتهاء صلاحية؟ خزّن (value, expiresAt) وتحقّق عند القراءة — عندها صار LRU + TTL، وهو الأشيع في cache الشبكة.
  • لماذا token bucket لا نافذة ثابتة؟ النافذة الثابتة تسمح بضعف المعدّل عند حدّ النافذتين (طرف النافذة الأولى وبداية الثانية).
SENIORنفّذ ترقيمًا لا نهائيًّا (infinite pagination) مقاومًا للسباقات
🎯 ماذا يختبر المُحاور؟الحالات الحدّية: نداءات متزامنة، الوصول للنهاية، الخطأ في منتصف التحميل، وإعادة التحميل أثناء التحميل.
class PagedList<T> {
  PagedList(this._fetch, {this.pageSize = 20});
  final Future<List<T>> Function(String? cursor, int limit) _fetch;
  final int pageSize;

  final items = <T>[];
  String? _cursor;
  bool _loading = false;      // ← يمنع النداءات المتزامنة
  bool _hasMore = true;

  bool get hasMore => _hasMore;

  Future<void> loadMore() async {
    if (_loading || !_hasMore) return;      // ← الحارس: أهمّ سطر هنا
    _loading = true;
    try {
      final page = await _fetch(_cursor, pageSize);
      if (page.length < pageSize) _hasMore = false;   // وصلنا النهاية
      items.addAll(page);
      _cursor = page.isEmpty ? _cursor : _cursorOf(page.last);
    } finally {
      _loading = false;                     // ← finally: يعمل حتى مع الخطأ
    }
  }

  Future<void> refresh() async {
    _cursor = null; _hasMore = true; items.clear();
    await loadMore();
  }
}

27Weak vs Strong Answers

نفس السؤال، ثلاث إجابات — الفرق بينها هو الفرق بين المستويات الوظيفية.

«ما هي Clean Architecture؟»

❌ WEAK

«معمارية فيها ثلاث طبقات: data وdomain وpresentation، وكل واحدة في مجلّد.»

🟡 BETTER

«تنظيم بطبقات مع قاعدة أن الاعتماد يشير للداخل، فالـdomain لا يعتمد على شيء خارجي، مما يجعل منطق الأعمال قابلًا للاختبار.»

✅ STRONG

«قاعدة اتجاه اعتماد قبل أن تكون مجلّدات: الاعتماد للداخل دائمًا، والـdomain يعرّف العقود ويُنفّذها الخارج (Dependency Inversion). أشتري قابلية اختبار واستبدال، وأدفع ملفات وقفزات أكثر. أطبّقها كاملة حين يكون المنطق غنيًّا أو الفريق كبيرًا، وللتطبيق البسيط أكتفي بحدّ أدنى: الـWidget لا ينادي الشبكة، وطبقة واحدة تعرف الـAPI.»

«أي state management تستخدم؟»

❌ WEAK

«Riverpod، لأنه الأفضل والأحدث.»

🟡 BETTER

«Riverpod غالبًا — أمان أنواع أفضل من Provider، ولا يحتاج context، واختباره أسهل.»

✅ STRONG

«يعتمد على نوع الحالة. المحلّية يكفيها setState. حالة الخادم أفضّل لها AsyncNotifier لأنه يعطيني التحميل والخطأ والإبطال جاهزة. لفريق كبير بتدفّقات معقّدة قد تكون صرامة Bloc ميزة لا عبئًا. وما يهمّني أكثر من المكتبة: مصدر واحد للحقيقة، تدفّق أحادي الاتجاه، وقابلية اختبار الحالة بمعزل عن الواجهة.»

«كيف تحسّن أداء التطبيق؟»

❌ WEAK

«أستخدم const وListView.builder وأتجنّب إعادة البناء.»

🟡 BETTER

«أفتح DevTools وأبحث عن الإطارات البطيئة، ثم أقلّل إعادة البناء وأحسّن القوائم والصور.»

✅ STRONG

«أقيس أولًا في profile mode — debug مضلّل. أحدّد أي خيط تجاوز الميزانية: UI يعني build/layout ثقيل، وRaster يعني رسمًا مكلفًا؛ العلاج مختلف تمامًا. ثم أغيّر شيئًا واحدًا وأعيد القياس لأثبت الأثر. لا أنثر RepaintBoundary بلا قياس — كل حدّ يكلّف ذاكرة وقد يُبطئ.»

«كيف تدمج LLM في تطبيق موبايل؟»

❌ WEAK

«أستخدم حزمة openai وأضع المفتاح في --dart-define ليكون آمنًا.»

🟡 BETTER

«أضع نداء الـLLM في الخلفية لحماية المفتاح، والتطبيق ينادي الخلفية بـtoken المستخدم.»

✅ STRONG

«وسيط خلفي إلزامًا — لا لحماية المفتاح فقط، بل لأنه المكان الوحيد الذي أستطيع فيه فرض حدّ معدّل، وتتبّع التكلفة لكل مستخدم، والتحكّم في الـsystem prompt، وتبديل النموذج بلا تحديث التطبيق، وتسجيل المخرجات للتقييم. ثم streaming بـSSE لخفض الزمن المُدرَك، مع تجميع تحديثات الواجهة كي لا أعيد البناء لكل token، وإلغاء يصل للخادم فعلًا كي لا أدفع مقابل توليد لن يراه أحد.»

🧠 النمط المشترك في كل إجابة قوية

  • تبدأ بـ«يعتمد على…» أو بذكر القيود — لا باسم تقنية.
  • تذكر ما تدفعه لا ما تكسبه فقط.
  • تذكر متى لا تفعل ذلك.
  • تُظهر عملية (قِس ← غيّر ← أعد القياس) لا نتيجة محفوظة.
  • تحتوي تفصيلة عملية واحدة لا يعرفها إلا من جرّب.

🎯 عن الخلاف: القاعدة الذهبية

لا تجعل نفسك البطل ولا الآخر الشرير. الصيغة الناجحة: «اختلفنا تقنيًّا. عرضتُ حجّتي بالبيانات — قِستُ الخيارين وأظهرتُ الفرق. اقتنع الفريق بالخيار الآخر لسبب لم أكن أعرفه [اذكره]. طبّقناه ونجح.» إظهار قدرتك على تغيير رأيك أقوى من إظهار أنك كنت محقًّا.

🎯 عن الخطأ الصعب: أظهر المنهجية لا الذكاء

«راقبت السلوك ← كوّنتُ فرضية ← قِستُ لأثبتها أو أنفيها ← عزلتُ السبب ← أصلحتُ ← أضفتُ اختبارًا يمنع عودته.» الجملة الأخيرة هي التي تفصل المهندس عن المصلِّح. وأضف: «واكتشفتُ لاحقًا أن السبب الجذري كان [قرارًا أقدم]، فعالجناه أيضًا» — يُظهر تفكيرًا في المنظومة.

   2. تحديد القيود        "بما أن الفريق ٣ أشخاص والموعد ٣ أشهر…"
   3. مقارنة الخيارات     "[أ] أسرع تسليمًا لكن أصعب توسّعًا…"

   5. القرار              "أختار [ب]"
   6. شرط الانقلاب        "وأراجعه إن حدث كذا"

🧠 لماذا تسمية التقنيات فورًا إجابة سيّئة؟

لأنها تُظهر أنك تصمّم بالعادة لا بالتحليل. المهندس الذي يختار Microservices قبل معرفة حجم الفريق سيختارها دائمًا — وهذا خطر توظيفي حقيقي. المُحاور يتخيّلك في اجتماع تصميم: هل ستسأل الأسئلة الصحيحة أم ستفرض قالبًا؟

وقول «لا أعرف، سأحتاج قياسًا» ليس ضعفًا — بل من أقوى الإجابات حين تكون صادقة، لأنها تُظهر أنك لا تخترع يقينًا.

إجابة واثقة وخاطئة أسوأ بكثير من «لست متأكّدًا، لكن تفكيري هو…». المُحاورون يوظّفون أشخاصًا سيعملون معهم لسنوات — ومن يخترع يقينًا في مقابلة سيخترعه في مراجعة كود وفي تقدير مدّة وفي حادثة إنتاج. الاعتراف بحدود معرفتك يُقرأ كنضج لا كضعف.

31Senior Engineer Checklist

علّم بندًا فقط حين تستطيع شرحه مع مقايضاته دون مراجعة.

  • أستطيع شرح Dart بعمق: الأنواع · null safety · const مقابل final
  • أفهم async والـEvent Loop والفرق بين Microtask و Event Queue
  • أفرّق بين Concurrency و Parallelism وأعرف متى يستحقّ Isolate تكلفته
  • أفهم مسار الرسم من Widget إلى Pixels
  • أفرّق بين Widget و Element و RenderObject وأعرف لماذا توجد ثلاث أشجار
  • أفهم Reconciliation وكيف يقرّر Flutter إعادة استخدام Element
  • أفهم الـKeys وأعرف متى تسبّب ضررًا
  • أفرّق بين rebuild و relayout و repaint
  • أختار إدارة الحالة بناءً على تصنيف الحالة لا على شهرة المكتبة
  • أفهم المعمارية كحدود واتجاه اعتماد لا كبنية مجلّدات
  • أستطيع شرح SOLID بأمثلة Flutter حقيقية
  • لديّ استراتيجية اختبار وأعرف ماذا أزيّف وماذا لا أزيّف
  • أفهم الشبكة: REST · رموز الحالة · JWT · تحديث الـtoken المتزامن
  • أفهم الأمن وأعرف أنه لا يمكن إخفاء سرّ في تطبيق موبايل
  • أستطيع تشخيص مشكلة أداء بالقياس لا بالتخمين
  • أستطيع تصميم نظام offline-first مع حلّ التعارضات
  • أستطيع تصميم أنظمة قابلة للتوسّع وشرح ما ينكسر أولًا
  • أفهم أساسيات الأنظمة الموزّعة: CAP · idempotency · eventual consistency
  • أستطيع دمج LLM APIs بمعمارية آمنة عبر وسيط خلفي
  • أفهم streaming وأعرف تحدّياته في الموبايل
  • أفهم RAG كخطّ أنابيب وأعرف كيف يُقيَّم
  • أستطيع مناقشة مقايضات AI: تكلفة · زمن · هلوسة · أمن
  • أستطيع شرح قراراتي المعمارية وأثمانها
  • أستطيع الدفاع عن قراري وتغييره أمام حجّة أقوى
  • أستطيع قول «لا أعرف» بثقة ومهنية
